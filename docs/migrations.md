# Basic commands

| Команда                   | Описание                           |
|---------------------------|------------------------------------|
| `pnpm migration:create`   | Create an empty migration          |
| `pnpm migration:generate` | Automatically generate a migration |
| `pnpm migration:run`      | Apply migrations                   |
| `pnpm migration:revert`   | Revert the last migration          |
| `pnpm migration:show`     | Show migration status              |

---

# Creating a Migration

## Creating an empty migration

```bash
NAME=create-users-table pnpm migration:create
```

Once the command has been executed, the following file will appear:

```txt
src/database/migrations/XXXXXXXXXXXX-create-users-table.ts
```

Where:

- `XXXXXXXXXXXX` — timestamp
- `create-users-table` — имя миграции

---

# Generating a Migration Automatically

If the following have been modified:

- Entity
- Columns
- Relations
- Indexes

you can automatically generate an SQL diff.

## Команда

```bash
pnpm migration:generate -- -n UpdateUsersTable
```

Либо:

```bash
pnpm typeorm migration:generate \
src/database/migrations/UpdateUsersTable \
-d src/database/datasource.ts
```

## What the team does

1. Builds the project:

```bash
pnpm run build
```

2. Compares:

- current entities
- current database state

3. Generates SQL changes

# Applying Migrations

## Running all new migrations

```bash
pnpm migration:run
```

## What happens

TypeORM:

1. Checks the `migrations` table
2. Looks for unapplied migrations
3. Runs them in order

---

# Reverting Migrations

## Reverting the Last Migration

```bash
pnpm migration:revert
```

## Important

This command calls the method:

```ts
down()
```

Therefore, every migration must correctly support rollback.

# Migration Example

## Creating a User Table

```ts
import {MigrationInterface, QueryRunner, Table} from 'typeorm';

export class CreateUsers1711111111111 implements MigrationInterface {
	public async up(queryRunner: QueryRunner): Promise<void> {
		await queryRunner.createTable(
			new Table({
				name: 'users',
				columns: [
					{
						name: 'id',
						type: 'uuid',
						isPrimary: true,
						generationStrategy: 'uuid',
						default: 'gen_random_uuid()',
					},
					{
						name: 'email',
						type: 'varchar',
						isUnique: true,
					},
					{
						name: 'created_at',
						type: 'timestamp',
						default: 'now()',
					},
				],
			}),
		);
	}

	public async down(queryRunner: QueryRunner): Promise<void> {
		await queryRunner.dropTable('users');
	}
}
```

# Recommendations

## 1. Always review the SQL

Before applying an autogenerated migration:

- review the SQL
- check for DROP operations
- check for nullable fields
- check for indexes

---

## 2. Do not edit old migrations

After applying to production:

- do not modify old migrations
- create new ones

---

## 3. Make rollbacks safe

The `down()` method must:

- delete only what was created
- correctly restore the schema

---

## 4. One task — one migration

Bad:

```txt
fix-users-and-orders-and-payments
```

Good:

```txt
add-user-avatar
create-orders-table
add-payment-status
```

---

## 5. Do not use `synchronize` in production

In production:

```ts
synchronize: false
```

Reasons:

- risk of data loss
- uncontrolled schema changes
- deployment issues

# Best Practices

## Use transactions

For complex changes:

```ts
await queryRunner.startTransaction();

try {
	// SQL operations

	await queryRunner.commitTransaction();
} catch (e) {
	await queryRunner.rollbackTransaction();
	throw e;
}
```

---

## Don't Store Business Logic in Migrations

Migrations should:

- modify the schema
- migrate data

But they should not:

- call services
- send HTTP requests
- use a DI container

---

## Test production rollback

Especially if the migration:

- deletes columns
- changes data types
- transfers data
